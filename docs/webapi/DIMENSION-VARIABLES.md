# Variables in width and height

The modal package sets `--visual-viewport-height` to a pixel value and uses it as the overlay height. Previously the native length parser treated `height:var(...)` as automatic, producing a tiny scrolling box. The retained reduced browser control reports 10px despite a 900px custom property, while Chromium reports 900px and responds to changing the property to 700px. In the actual Add Party diagnostic a replacement input moves ten pixels inside a five-pixel modal scroller, triggering a new focus scroll after the readiness helper finished. This is a dimension-resolution defect, separate from changed-target event delivery. Full app closure requires the targeted rerun.

Width and height now retain a pending whole-value `var()` through the existing cascade and resolve it before computed-style memoization. Supported values are existing numeric/viewport lengths, whole-variable aliases and nested fallbacks. Custom-property lookup uses the defining element before inheritance; inline/sheet importance and ordinary invalidation remain effective. Resolution is bounded to 32 nested values, 128 visits and 4096 bytes per value. Cycles in supported aliases/fallbacks invalidate the custom property; missing or invalid custom properties may use an outer fallback. An existing value that is invalid as a length computes to automatic rather than reviving an earlier width/height declaration.

This follows the relevant [CSS Variables rules for cycles, substitution and inheritance](https://www.w3.org/TR/css-variables-1/). It is a bounded dimension subset: no general token-stream substitution, `calc()` arithmetic, registered custom properties, animation tainting, full CSS-wide keyword cascade or arbitrary shorthand resolution. Computed custom-property string reflection retains the existing as-written surface; this increment resolves dimensions, not every CSS property. Unsupported length expressions remain automatic. No special modal class, rectangle or variable name is recognized.
