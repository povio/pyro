At 2px padding the preceding inline-flex assertion fails in Chrome and skips cleanup. The next grid case therefore *starts* hidden, auto or scroll rather than visible. In Pyro that predecessor passes. `trace.cjs` derives three fixtures from the pinned WPT: instrumented original order preserving assertion/cleanup behavior, fresh target per case, and separate boxes for before/after. Full receipts include names, statuses, both computed overflow axes and the four numerical reads.

**Unpadded root cause:** the grid's 0px-wide, 2000px-tall track contributes to Pyro's scrollable region even without grid items. The 96 fresh controls reproduce this with `contain:none` and `contain:layout`, explicit and implicit tracks, and empty grids. In both engines a nonzero container width, horizontal padding, or a wide child preserves tall overflow. Vertical padding alone leaves the difference. This is not evidence for a containment-specific exclusion or a grid-track sizing change. [CSS Grid 2 §5.3](https://www.w3.org/TR/css-grid-2/#overflow) explicitly includes the grid in the overflow region, while [CSS Overflow 3 §2.2](https://www.w3.org/TR/css-overflow-3/#scrollable) excludes zero-area **border boxes**. That exclusion does not expressly cover a track region. Pyro also intentionally retains single-axis overflow for empty tracks (`bb75979c`). No blanket empty-axis suppression or change to reverse-axis behavior proposed. Independent QA should assess whether to treat discarding degenerate grid overflow as a compatibility policy rather than a standards fix.
