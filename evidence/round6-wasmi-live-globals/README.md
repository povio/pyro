# Wasmi scalar Global interoperability experiment

This is a separate experimental child of `86f4b697544ba8e1989eb5d9fdeb36c4135e1fa9` (Wasmi 2.0.2 auto/tail dispatch). The host JavaScript engine remains the unchanged pinned JSC archive `0e0dd7038a7a-6f4649e395e0`. The archived predecessor's binary SHA-256 is `35b0c6f3643f65f511b6114e9982b33736863fbc5d6c2895a6594e845dbd5498` and the measured new binary is `90518322e4738a6f788e650ebb6c14cbb66739380e38552d6b455dc65360c5c8`. The new implementation changes only experimental branches. It is unconditional when someone builds the experiment, not a production feature toggle. No production browser, runtime flags or dependency list was changed. No previously faulting module or ambiguous native-risk WPT URL was run; no application or synthetic interop fixture was sent to the shipped JSC backend.

## Implementation and ownership

The JS API now wraps actual Wasmi Global handles for signed i32, i64/BigInt, f32 and f64. An instance can import a mutable Global, re-export the same object and read subsequent JS or Wasm writes. Immutable numeric primitives can also be imported. The public JS wrappers expose a view of real cells, without copying values between runtimes. The parser preserves native global indices for re-exports and duplicate export names. Creating independent instances gives distinct internal global state. The Wasmi engine/store registry and JS WeakMap for Global slots are agent-scoped through pyro-js's existing root-context cache. Window realms in the same agent can pass a live Global; a dedicated worker owns its own registry. This does not implement structured clone or cross-agent transport.

The original per-instance RefCell borrow denied reentry during host functions. The new bridge reborrows Wasmi's documented Caller/StoreContextMut from the innermost active import, using scoped-tls-hkt 0.1.5 with scoped Rust lifetimes. JS callbacks may call back to the same instance, traverse a different store and return to an outer store, or touch an existing Global during a start function. The active call stack roots the right JS import array and preserves thrown exception identity at each nesting level. Nested calls into the same store spend the outer fuel budget. The Wasm host exposes no raw memory pointer or Wasmi handle to page code. Function boundaries remain limited to the previously implemented numeric subset; i64 Global values work independently of i64 function-boundary interop.

A global-linked Wasmi arena is referenced weakly by the runtime and strongly by live JS-backed objects. Wasmi's public API does not reclaim individual instances, trampolines or cells from a live arena. As long as one related wrapper remains live, native objects from other, unreachable JS wrappers can persist. The experimental arena therefore admits at most 256 links, 16 MiB cumulative encoded module input and 4,096 cumulative conservative Global-slot reservations. Failed links and aliases can consume admission. A shared arena is limited to four memories and eight tables, in addition to existing per-memory, per-table and per-call bounds. The encoded-input cap is not a total heap cap. A deterministic no-memory test established that the 257th link is rejected before start while the original Global and an independent store remain usable. This bounds retention without fixing the underlying per-object reclamation limitation. The Wasmi Global object is agent-shared; compiled Module wrapper branding remains realm-local.

## Table boundary

Wasmi 2.0.2's documented public API supports real store-owned tables. `table-control/` independently imported one native funcref table into two Wasmi instances and re-exported it. Changing the slot through the second handle changed indirect calls in both instances (10, then 18 and 14). Growing the table by one was visible through the alias. This used only the Rust Wasmi API and supplied no JavaScript Table implementation. The browser still has no Table constructor or live Table import/export binding. A real bridge must preserve canonical JS exported-function wrappers and the original imported function's JS callback when invoked indirectly from another instance. Arbitrary JS externrefs in tables also require GC tracing with overwrite/collection semantics: simply pinning all JS values in a Wasmi store can retain cycles indefinitely. Memory/ArrayBuffer aliasing, streaming, ESM, GC proposal features and deployment remain unqualified. No raw backing-memory path is proposed.

## Performance method

Five fresh processes per browser/build, rotated at concurrency one, verified the previously independently generated 16,384-sample PCM 15-tap FIR output for each of eight gains. The direct stage calls the existing FIR kernel; a second stage uses a separate function-imported Wasm bridge, and the live-Global stage updates a JS gain cell before invoking a Wasm driver that reads that cell and dispatches to the same kernel through its host callback. Every invocation checks the independent digest, and the harness checks exactly one callback per block in the two driver cases. The old Wasmi build could not instantiate the live-Global driver and has no timing for it. Each reported wall sample uses two warm-up batches and five measured batches of 32 blocks. Full raw data and per-process medians are in `application-results.json` and `summary.json`. The host was severely loaded; timing dispersion is a material limitation.

The source patch and measurements are private experimental evidence; none of these names may be counted in the shipped LP score.
