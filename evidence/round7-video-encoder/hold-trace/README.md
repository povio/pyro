The pinned test configures directly without a capability check. In both subtests it enqueues an input and calls flush(), then awaits firstOutput **before** attaching the expected AbortError handler to the flush promise. Only the output callback calls reset() and resolves firstOutput. The first test installs getDefaultCodecInit(t)'s error callback, which invokes the 'unexpected error' assertion. In the second, createVideoEncoder(t, callbacks) has no supplied callbacks.error: its fallback constructs t.unreached_func('unexpected error()') but never invokes the returned function. The error callback cannot resolve firstOutput. For these unsupported codecs the configure failure happens before an encoded output exists, leaving firstOutput pending and the flush rejection unhandled by this test. The attempted second configure/flush inside the second test's output callback is unreachable. This is control-flow attribution, not a claim those internals were originally logged. Window final receipt text corroborates the rejection; the worker receipt only corroborates the timeout. Neither shows a stuck native encoder or a failed reset.

A separate minimal ordinary configure+flush control was necessary to establish whether the flush itself settled. On the frozen executable, both Window and DedicatedWorker observed the same sequence for both codecs: isConfigSupported false; configure returns with state configured; error callback receives NotSupportedError with closed state and encodeQueueSize zero; the already-handled flush promise rejects with the same error name/message, closed state and zero queue size. No output occurred. No frame was submitted in this control; queued frame disposal on the WPT path is source-verified, not instrumented. video_encoder.js clear() invalidates the epoch, releases queued encode frames, zeroes the queue count, rejects pending flushes and clears the list before invoking the error callback. ## Color precedence

WebCodecs §4.6 Output VideoFrames steps 4 and 5 first detect the stream color space, then assign the active decoder configuration's colorSpace when it exists. The UA may fill null members from corresponding detected values. All four members of the explicit override in our control were non-null, so that permission cannot replace them. The VideoDecoderConfig.colorSpace definition also says it configures output VideoFrame.colorSpace. https://w3c.github.io/webcodecs/#output-videoframes and https://w3c.github.io/webcodecs/#dom-videodecoderconfig-colorspace .

Original FFmpeg bitstream trace and ffprobe independently identified SMPTE 170M primaries, matrix and transfer, with limited range. In the existing normal control LP reported RGBA/sRGB and [255,0,0,255] for omitted/empty colorSpace, its pre-existing path. For an explicitly specified non-null limited BT.709 override it returned I420 with that BT.709 metadata and [255,40,0,255]. Signed stable 158.0.8127.37 reported the in-band SMPTE 170M metadata and [254,0,0,255] for all three cases, including the override. On this fixture the explicit LP result follows the specified precedence, while the signed browser preserves the in-band values. This evidence establishes behavior for the tested AVC configuration, not arbitrary color transforms.
